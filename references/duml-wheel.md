# DUML 里那些 evdev 看不到的输入

> 实测机型：DJI RC Plus 1（RM700B，`ro.product.model=DJI RC Plus`，
> `ro.board.platform=kona`，Android 10）。2026-11-15 验证。

这篇讲两个输入：**右拨轮下方那个不回中的滚轮**，和 **F/S/N 三档飞行模式拨杆**。
它们的共同点是：`getevent` 里完全没有，只在 DUML 的同一个状态包里。

## 结论先说

遥控器上有两个输入**不在 `/dev/input` 的任何节点里**，但**一直在 DUML 里正常上报**：

| 输入 | 位置 | DUML 字段 | evdev |
|---|---|---|---|
| 第三拨轮（不回中） | `0x06/0xAE` **byte 4** | 相对量（方向+速度） | 没有 |
| 飞行模式拨杆 F/S/N | `0x06/0xAE` **byte 2** | 位置量（三档） | 没有 |

所以：

- `getevent -lp` 找不到它们 ≠ 硬件没装 ≠ 固件不支持
- 两个都**不需要接线、不需要拆机**，现在就能读
- 而且**不需要飞机在线** —— 遥控器自己就在报

## 为什么 evdev 这条路上肯定没有

```
/dev/input/event6  "DJI embedded joystick"
  B: EV=20000b        → SYN(0) + KEY(1) + ABS(3) + FF(21)
  ABS_X / ABS_Y   ±32767    左摇杆
  ABS_RX / ABS_RY ±32767    右摇杆
  ABS_Z  / ABS_RZ 0..255    左右两个自回中拨轮
  ABS_HAT0X / HAT0Y -1..1   五向键
```

关键在这个 `EV=20000b`：**没有 `EV_REL`（第 2 位）**。

Linux 输入子系统里，"不回中的滚轮"的标准上报方式是 `EV_REL / REL_DIAL`
（拧一格报一次 +1/-1，没有"位置"概念）。event6 连这个能力位都没声明，
说明内核侧压根没注册这一路。另外 `ls /dev/hidraw*` 为空 ——
也没有绕开 evdev 的独立 HID 通道。

## DUML 怎么读

### 1) 打隧道

`40007` 是遥控器自己 loopback 上的端口（`LISTEN, uid 0`），必须从 PC 侧转发：

```bash
adb forward tcp:40007 tcp:40007
```

### 2) 帧格式

```
55 CC 30 75 | uint32 LE 载荷长度 | 载荷
```

载荷里：

| 偏移 | 含义 |
|---|---|
| 9 | cmd_set = `0x06` |
| 10 | cmd_id = `0xAE` |
| 11..27 | 17 字节状态数据 |

### 3) 必须发心跳，否则会被踢

每 **40ms** 一个 keepalive（cmd_set `0x00` / cmd_id `0x01`，app(2) → RC(6)），
带 CRC8（头）和 CRC16（整体）。不发的话 DJI 的协议服务会关掉连接。

> ⚠️ **2026-11-16 修正**：早先记的"两个客户端同时连没问题"是错的。
> 多客户端会**抢包 + 抢遥控器的处理能力**（实测 20 秒只收到 11 包，
> 正常应约 77 包）。更要命的是**飞行时**：飞行链路自己也走 DUML，
> 我们的常驻客户端会和它抢 → 用户实测"打杆不丝滑、极限转角不及时"。
> 所以**仪表线程必须跟随游戏生命周期**：游戏在=连，游戏退/飞行=断
> （rcplus_sim 已实现，见下方"DUML 客户端生命周期"）。

### 4) 17 字节状态包结构

| 字节 | 含义 |
|---|---|
| 0, 1 | 固定 `00 00` |
| **2** | **飞行模式拨杆 F/S/N（位置型）** |
| 3 | 固定 `00` |
| **4** | **第三拨轮（相对量）** |
| 5..6 | 右摇杆 X（int16 LE，中心 1024） |
| 7..8 | 右摇杆 Y |
| 9..10 | 左摇杆 Y |
| 11..12 | 左摇杆 X |
| 13..14 | 左拨轮 |
| 15..16 | 右拨轮 |

六个轴都是 **int16 LE，中心 1024，满行程约 ±660**。
所以一个"静止"的状态包长这样：

```
00 00 02 00 00 | 00 04  00 04  00 04  00 04  00 04  00 04
                    ↑ 六个 0x0400 = 1024
```

### 5) 滚轮字节的编码

| bit | 含义 |
|---|---|
| 7 | 转动中（静止时整字节为 `0x00`） |
| 6 | 方向（1 = 屏幕上的 ▶ / 右，0 = ◀ / 左） |
| 5..1 | 速度档 1~5（实测能拨到 4；边沿会出现 0） |
| 0 | 恒为 0 |

实测取样：

```
0x82 → 左 1 档      0xC2 → 右 1 档
0x84 → 左 2 档      0xC4 → 右 2 档
                    0xC6 → 右 3 档
```

**方向已由用户实机确认**：`0xC*` 确实对应手往 ▶ 方向拧。

## byte 2：飞行模式三档拨杆（F / S / N）

左肩下方那个三档拨杆，**位置型**（拨到哪停在哪，会一直保持）。

| byte 2 | 档位 | 实测 |
|---|---|---|
| `0x02` | **F**（上档） | 停住 8.6 秒不动 |
| `0x00` | **S**（中间） | 停住 7.3 秒 |
| `0x01` | **N**（下档） | 停住 47.3 秒 |

映射是**实测确认**的（仪表上 F/S/N 灯和物理位置一一对上，2026-11-15）。

**稳定性**：静止 25 秒收到 251 个包，`byte2` 一次都没跳变 —— 是干净的位置量，
不是脉冲。可以直接当输入用。

**注意**：拨动时一定会**路过中间档**，所以会看到 `F → S → N` 这样的中间态。
这不是抖动，是滑动开关的物理特性：

```
[67.5s] N → S → F → S → N → S → F
[82.4s] F → S → N → S → F → S → N → S → F
```

**没有任何飞机连接时它也在报** —— 这点很重要，说明 Flight Mode 属于遥控器
自己的状态，不依赖 OcuSync 链路。

### 为什么一开始会误判

第一版状态包里 `byte2` 看起来在 `00/01/02` 之间 1 秒跳一次，像是噪声。
真相是当时手在拨它。判据是**静置时长**：位置型会长时间停住（本次最长 47 秒），
计数器/心跳则永远在跳。所以排查这类字段时，必须录"停住不动"的数据，
而不是录"边拨边看"的数据。

## 刷新率

| 状态 | 实测 |
|---|---|
| 静止 | **9.7 包/秒**（约 100ms 一个） |
| 拨轮转动时 | 设备**立刻补发**状态包，相邻变化最短 **20ms** |

所以滚轮不是"100ms 才反应一次"，而是事件驱动的。做输入用足够。

档位拨杆只受 10Hz 采样限制：拨到位之后**最迟 100ms** 反映到 `byte2`。

## 和 RC Plus 2 的关系

RC Plus 2（TKPL2）的同类项目里，`byte 4` 就是右上滚轮 —— 位置、编码完全一致。
也就是说 RC Plus 1 的固件**也实现了这一路**，只是没往 evdev 里映射。

## DUML 客户端生命周期（2026-11-16 新增，重要）

用户报告：加上滚轮/FSN 功能后，**遥控飞机时打杆不丝滑、极限转角不及时**；
上一版（没有 DUML 客户端）是顺滑的。定位过程（五轮探针）：

| 排除项 | 证据 |
|---|---|
| WiFi 射频 | ping 中位 2ms / 最大 20ms（60s） |
| CPU | sim 进程 3.8% 单核 |
| "双实例" | venv stub 的父子进程误判，实际单实例 |
| 事件流基线 | `getevent` 间隔中位 2ms，干净 |
| 25Hz 心跳本身 | 合成探针：漂移仅 +12ms |
| 电量查询 | dumpsys 185ms，未见挤停 |

剩余证据：任何 adb 命令会让事件流攒包 100~370ms（内核时间戳证实
数据被传输层攒住）；DumlWheel 开启时出现 688ms 设备端内核断档。
结合用户"上一版顺滑"的关键对照 → 结论：**常驻 DUML 客户端在飞行时
与飞行链路争抢遥控器（MCU/协议服务）的处理能力**。

修复（已实现）：

- `dashboard.stop_wheel()` / `dashboard.wheel_running()`：断开/查询
- `rcplus_sim`：启动不连；游戏启动才连；主循环每 2 秒随动
  （`game_pids()` 空 → `stop_wheel()`）；R3 关游戏、finally 退出兜底
- `stick_screen`（手动仪表）：保留常驻连接但打印警告

**原则：飞行 = 遥控器独占 DUML，模拟器的任何 DUML 客户端都不得在线。**

## 踩过的坑

1. **索引别数错**：`p` 是 `bytes`，`byte 4` 是 `p[4:5]`；
   如果误当 hex 字符串去切 `p[8:10]`，抓到的是左杆 Y 的噪声，
   会看到满屏假变化（真踩过，浪费了一轮录制）。
2. **adb server 重启后 forward 会丢**，报 `no devices/emulators found`。
   无线串号要顺手补一次 `adb connect <ip>:5555` 再 forward。
3. **端口 40007 可能被上一次运行的残留占着**（`cannot bind: 10048`）。
   这时不要慌 —— 连上去照样能用，说明已经有一条到同一台机器的隧道。
4. **不要用 `pkill -f getevent` 清理**，会把自己那个 shell 一起杀掉。
   正确做法：
   ```bash
   ps -A -o PID,ARGS | grep 'getevent -lt' | grep -v grep | \
     awk '{print $1}' | xargs -r kill -9
   ```

## 还没做

两者目前都**只显示，不参与手柄输出**。滚轮的原因是 Xbox 360 虚拟手柄的
六个轴已经排满了（两摇杆 + 两拨轮占 LT/RT），要给它一个轴就得征用别人的位置。

档位拨杆不一样 —— 它天然适合映射成**离散按键**（三档 = 三个键或两组键），
不占轴资源。真要接的话这是最省事的那个。

可选方案：

- **鼠标滚轮**（`SendInput` MOUSEEVENTF_WHEEL）：不占手柄资源，语义也最自然
- **按键脉冲**：一格发一个键，适合 turtle mode / 重置 / 切视角
- **位置轴**：累积成 0~100 的滑块，但得占掉 LT 或 RT 之一
- **档位 → 三档开关**：F/S/N 映射到 3 个按钮（或 2 个按钮的组合），
  可用来切换游戏内的灵敏度/相机模式
